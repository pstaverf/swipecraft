# Донат Swipecraft (этап 5)

## 0. Честная рамка

На Bedrock Dedicated Server **нет API приёма платежей**. Поэтому донат устроен как
«игрок подаёт заявку → админ проверяет платёж вне игры → одобрение выдаёт бонусы»:

- скрипт никогда не начисляет тариф сам и не списывает деньги;
- `submitRequest` только регистрирует заявку и зовёт админов;
- все бонусы включаются ровно в момент `decideRequest(approve)`;
- возврата в скрипте нет вообще: `DONATIONS.refundAllowed = false`, откат возможен
  только отзывом тарифа (`revokeTier`), выданные кейс-ключи не отзываются.

Это осознанный выбор: «автоматический донат» на BDS — это дыра, через которую
кто угодно выдаст себе тариф подменой ответа платёжки.

## 1. Тарифы

`DONATIONS.tiers` (цена в `DONATIONS.currency`, перемножается на `priceMultiplierRub`):

| Тариф | Цена | Дней | Ключей/мес | Приоритет входа | Частицы | Префикс |
|---|---|---|---|---|---|---|
| `bronze` | 199 ₽ | 30 | 2 | да | нет | `§7[§8бронза§7]§r` |
| `silver` | 399 ₽ | 30 | 5 | да | да | `§f[§7серебро§f]§r` |
| `gold` | 799 ₽ | 30 | 10 | да | да | `§6[§eзолото§6]§r` |

Длительность при выдаче: `minDays` 7 … `maxDays` 120. Донат **не даёт** монет,
предметов в руки, кейсов «за деньги» и никаких преимуществ в PvP — только ключи к тем
же кейсам, что открываются за ₡, косметика и очередь.

## 2. Заявка и решение

```
/sw:don → «Подать заявку» → submitRequest(player, tier, days, note)
```

- у игрока может быть только **одна** открытая заявка: повтор отклоняется с
  указанием id первой (иначе спам в очереди админов = способ спрятать нормальную заявку);
- id заявки — короткие base36 (`время + соль`), хранятся последние `requestsMax` = 80;
- заявка уходит в `sw:don:requests`, в аудит (`donate/request`) и всем онлайн-админам
  в чат (`[donate] заявка #id: Name → tier на N дн. (комментарий)`);
- в комментарии игрок пишет **идентификатор платежа** — это единственная связка
  «заявка ↔ платёж», проверять её человек будет по нему;
- `decideRequest(actor, id, approve)`:
  - уже обработанную заявку повторно решить нельзя («заявка уже обработана»);
  - при одобрении → `applyTier` + уведомление игроку, если он онлайн;
  - при отказе → статус `rejected`, `by = actor`, игроку — `don.rejected`.

Заявка подаётся из `/sw:don`: выбор тарифа → поля «дней (7…120)» и «Discord / ID»
(комментарий ≤ 90 символов, режется до этой длины) → подтверждение.

Ручная выдача/отзыв — админ-вкладка «Донат»: «Заявки · N», «Выдать тариф»,
«Отозвать тариф», «Журнал выдач», «Очередь входа», «Отпустить всех». Все пути идут
через `applyTier`/`revokeTier`, поэтому в журнале нельзя отличить «выдал за деньги»
от «выдал руками» — там всегда указан `actor`.

## 3. Что именно включается

`applyTier`:

- `donorUntil = max(now, donorUntil) + days` — продление суммируется, а не обнуляет
  остаток (купил ещё на месяц — получил +30 дней, а не «сгорело»);
- запись в `sw:don:grants` (300 последних: время, actor, игрок, тариф, дни, note);
- `refreshNameTag(player)` — префикс в `nameTag`;
- `autoGrantKeys(player)` сразу (не ждём следующего цикла);
- сообщение игроку `don.thanks` со датой окончания.

Прокси-поля не хранятся: `tierOf(player)` каждый раз сверяет `donorUntil` с часами,
так что истёкший тариф **перестаёт работать мгновенно**, даже если игрок не выходил из
игры; при сбросе тарифа в `none` префикс с `nameTag` снимается в том же вызове.

## 4. Ежемесячные ключи

`autoGrantKeys` (задача `meta-unlock`, раз в 200 тиков на каждого игрока):

- счётчик `sw:don:usage` хранит `{ month, keys }` на игрока, месяц — UTC-календарный;
- пока `month` совпадает с текущим — повторной выдачи нет, сколько бы раз задача
  ни прогнала;
- сумма = `DONATIONS.keysPerMonth[tier]` (2 / 5 / 10);
- если игрок офлайн, ключи всё равно **начисляются в его кошелёк** (`meta.caseKeys`)
  с пометкой в журнале экономики — «не зашёл в месяце» не означает «потерял».

Ключи тратятся в `/sw:case` (`casePrice()` → `{ coins, keys }`), то есть донат
покупает те же вскрытия, что и фарм, только быстрее.

## 5. Косметика

- `swipecraft:donor_trail` вокруг игрока раз в `trailEveryTicks` (10 тиков, бюджет 3 мс),
  для тарифов с `particles: true` (silver, gold);
- если кастомная частица не загрузилась (игрок без ресурспака) — фолбэк
  `minecraft:basic_smoke_particle`; ошибка на одном игроке не останавливает обход
  остальных;
- префикс имени — см. выше. Ни лута, ни статов косметика не даёт.

## 6. Приоритетный вход

Очередь нужна не «для красоты», а чтобы на переполненном сервере донер попал в игру,
а не ловил таймаут подключения:

- пороги в тюнингах: `queueEnabled` (вкл/выкл на ходу), `queueSoftCap` 82,
  `queueReleaseAt` 74 — гистерезис, чтобы не дёргать игроков на флуктуациях онлайна;
- при входе (`playerSpawn`, `initialSpawn`) онлайн выше `queueSoftCap` и игрок не
  донер → его ставит в точку `QUEUE.waitSpot`, вешает тег `sw:queued` и раз в
  `meta-queue` (20 тиков) показывает action-bar «ждёшь N с, онлайн X, кап Y»;
- как только онлайн упал до `queueReleaseAt` — игрок отпускается сам, теги снимаются;
- донер проходит мимо очереди (`isPriorityPlayer`), и если тариф выдали **во время**
  ожидания — игрок отпускается на следующем тике, заявку переоформлять не нужно;
- на постановку в очередь даётся `grantGrace(player.id, 15_000)` в античит:
  телепорт в зал ожидания не должен быть засчитан как «игрок телепортировался сам»;
- админ может отпустить всех вручную (кнопка «Отпустить всех» → `releaseAll`) и
  посмотреть состав ожидающих (`queueReport`, там же — «Очередь входа»).

Очередь не кикает и не держит игрока в аду: он в мире, в безопасной точке, и выходит
из очереди в течение секунды после освобождения слота.

## 7. Хранилище

| Ключ | Что | Лимит |
|---|---|---|
| `sw:don:requests` | заявки (все статусы) | 80 последних |
| `sw:don:grants` | журнал выдач/отзывов | 300 последних |
| `sw:don:usage` | счётчики ключей по месяцам | по игроку |

Всё — через `saveWorldJson` (чанки + debounce), как и остальной мета-слой.

## 8. Что проверяет стаб-харнесс

`npm run stability` (раздел `donations`, `queue`): заявка уходит админу и сохраняется,
дубликат открытой заявки отклоняется, одобрение выдаёт тариф + префикс имени + запись
в журнал, авто-выдача ключей донеру, приоритетный вход отпускается раньше остальных.

Живой клиент дополнительно проверяет: отображение префикса `§7[§8бронза§7]§r` на
мобильном клиенте и частицу `swipecraft:donor_trail`.
