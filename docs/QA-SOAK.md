# QA: стаб-прогон и soak (симуляция сервера на моке Script API)

Документ о том, **как мы ищем баги мета-слоя без живого BDS**: два headless-прогона на
одном и том же моке `@minecraft/server` / `@minecraft/server-ui`.

| прогон | команда | вопрос, на который он отвечает |
| --- | --- | --- |
| stability | `npm run stability` | «работает ли фича так, как задумано» — 134 рукописные проверки по сценариям |
| soak | `npm run soak` | «не разъезжается ли состояние сервера при беспорядочном потоке» — 23 инварианта после каждого раунда |

Оба завершаются с `exit != 0`, если найдено хоть что-то, поэтому их можно повесить на CI.

## 1. Запуск

```bash
npm run stability                      # сценарии + guard-проверки, ~2 с
SOAK_SEED=7 SOAK_PLAYERS=24 SOAK_ROUNDS=400 npm run soak   # стресс/фазз, детерминированно
SOAK_VERBOSE=1 npm run soak            # печати каждого раунда: что видел каждый аудит
```

* `SOAK_SEED` фиксирован (`20261113`) — провал обязан воспроизводиться тем же сидом,
  поэтому ГПСЧ свой (`mulberry32`), а не `Math.random()`.
* `SOAK_PLAYERS`/`SOAK_ROUNDS` — размер roster'а и число раундов. Каждый 5-й игрок — админ,
  треть стоит на спавне, часть говорит по-английски: привилегии и язык меняют поведение,
  и проверка без них ловила бы только «обычного» игрока.
* Оба прогона сначала собирают бандл (`tools/stability/build.mjs`), исходники трогать не нужно.

## 2. Как устроен soak

1. **Бут** — ровно как в бою: `beforeEvents.worldLoad` → `startup`, регистрация кастомных
   команд, `worldLoad`, 6 тиков. Никаких «тестовых» конструкторов состояния.
2. **Мешок действий** (`WEIGHTS`): меню и команды, `caseRush`, `shopBuy`, `questTwice`,
   `marketSell`, `acBurst`, `totemForge`, `quarryRush`, `massJoin`, `rankRoll`, копание и взрывы, вёдра,
   PvP, смерть, логауты, `mint`, `timeWarp`, `restart`, `toggles`, `adminCommands`. На каждом
   действии — аргументы «злые»: пустые строки, `-1`, `999999`, `drop`, `..`, не существующие id.
3. **Формы играются по-настоящему**: `validModal` отвечает на `ModalFormData` допустимым
   значением (dropdown → 0, slider → максимум, toggle → true), `walkMenu` ведёт по подписям
   кнопок. Ответ «cancel» на пустой форме означал бы, что ни одна покупка не случилась, а
   аудит рад рапортовал бы «нарушений нет» — это главный способ, которым такие проверки врут.
   Метки кнопок задают **списком альтернатив** (`["Кейсы", "Cases"]`): треть ростера говорит
   по-английски, и поиск по одной русской подписи тихо превращался в «cancel» — путь не
   проходил, а проверки молчали. Ответы отдаёт политика мока (`ui.policy`), а не очередь
   `ui.answers`: очередь глобальна и съезжает на шаг, если в середине пути всплывает
   посторонняя форма.
4. **Аудиты** (23) сверяют состояние после каждого раунда: эмиссия
   (Σ монеты + lockedCoins + ledger = minted − burned), купол спавна, `txCount`, схема
   кошелька, кошельки ≤ числа когда-либо созданных игроков, скоринг античита и волна киков,
   ранги, HUD и сайдбар, кланы, карьеры, тотемы, кейсы/косметика, рынок, бюджет DP, тексты
   чата и форм, таймеры и память.

### Анти-вакуум

Пустой аудит опаснее отсутствующего: он печатает «OK» и ничего не проверяет. Поэтому:

* **`reached`** — счётчики «доходило ли действие до состояния». Если путь не пройден, прогон
  печатает `пути, до состояния которых soak не дошёл (аудиты по ним молчат): …`.
* **`аудиты без данных`** — аудиты, чей последний отчёт звучит как «нет …» / «0 записей».
* **мутация** — каждая новая проверка обязана быть проверена «откатом»: правишь код так, чтобы
  поведение сломать, — прогон обязан покраснеть. Прогнанные мутации этого этапа:

| мутация | прогон | результат |
| --- | --- | --- |
| `idOf()` снова через `Math.random()` | stability | `провалов 1` — «из 5000 id уникальных только 1275» |
| `sendPaged` → одно `sendMessage(join)` | stability | `провалов 2` — пагинатор + лимит 900 |
| `stats.pulls += 1` выключен | soak | `нарушений: статистика кейсов не сходится с кошельками ×20` |
| `resetState` на `playerLeave` удалён | soak | `нарушений: античит копит состояние ушедших игроков ×8` |
| `resetState` возвращён на `playerSpawn` | stability | `провалов 1` — скор обнуляется респауном |
| цена кейса рангов ×2 | soak | `крутка кейса рангов не дошла до состояния ×15` |
| цена открытия кейса ×2 | soak | `пуск кейса не дошёл до состояния ×8` |

## 3. Что нашёл этот прогон

Все пункты исправлены в коде, а не ослаблением проверок.

1. **Дубликаты идентификаторов записей.** `market.idOf()`, id клана и id заявки доната
   строились как `Date.now().toString(36) + Math.floor(Math.random() * 1296).toString(36)`.
   Пачка записей за одну миллисекунду (массовая выставка лотов, волна заявок) сталкивается по
   закону дней рождения, а id — ключ поиска («выкупить лот `lp…`»): дубликат = «продал не то».
   Заменено на `uniqueId(prefix)` (время + монотонный счётчик, `src/kernel/util.ts`).
   Soak ловил это как `дубликат id лота` на сиде 555.
2. **Отчёты обрезались клиентом.** `player.sendMessage(lines.join("\n"))` в админских экранах
   давал сообщения 1000+ символов; Bedrock режет их, и хвост сводки («циркуляция: …») терялся
   молча. Добавлен `sendPaged` (`src/ui/common.ts`) — упаковывает строки в сообщения ≤ 900 и
   режет поперёк только откровенно гигантские строки; синхронный ответ команды режет `clip()`
   (`src/commands/registry.ts`) — по границе строки и с пометкой «… ещё N строк». Проверка
   длины сидит и в стабе (по всему журналу чата), и в soak (по курсору новых строк, лимит 900).
3. **Античит забывал подозрения после смерти.** `playerSpawn` вызывал `resetState`, то есть
   `score = 0`. Игрок мог обнулить себе историю детекторов одним «прыжком в лаву» или
   переподключением. Теперь на спавне остаётся только `grantGrace` (окна частот он и так чистит),
   накопленный скор снимает только затухание по времени.
4. **Утечка памяти детекторов.** `grantGrace` звал `stateOf(id)`, который *создаёт* запись.
   Из отложенных задач (карьер, граница, ртп) это рисовало состояние и для игроков, которые уже
   вышли: `playerLeave` к тому моменту отработал, вычищать некому. Теперь грейс выдаётся только
   тем, кто в мире; `acTrackedCount()` + аудит «состояний ≤ онлайн + запас» это сторожат.
5. **Неподставленные плейсхолдеры в текстах.** `don.you` печатал `{rolls}` (аргумент назван
   `keys`), кнопка карьера — литерал `{cost} {symbol}`, у KoTH subtitle ехал `{seconds}`.
   Системно закрыто guard'ом в `substitute()` (`src/kernel/i18n.ts`): если после подстановки в
   строке остался `{имя}`, пишется `log.warn("i18n", …)` ровно один раз на ключ, а стаб
   проверяет guard, сам ломая `rtp.done`.
6. **Починка спавна не доезжала до всех клеток.** `pendingPins` обрезался бюджетом за проход,
   а `repair`/`check` не доходили «до конца» — список критических клеток собирался неполно.
   Теперь `startSpawnBuild(..., { sweep: true })` для `repair` чинит всё, `checkSpawnIntegrity`
   сам запускает точечный ремонт, и стаб прокручивает сборщик прямыми `spawnBuildTick()`.
7. **Ложные срабатывания самих проверок** (тоже баки, но тестовые): сравнение по сохранённому
   JSON ловило такт автосейва, а не состояние (`монеты списаны, а косметики нет ×9/×17`,
   «статистика кейсов не сходится» на 60 игроках). Вывод зафиксирован правилом ниже.

## 4. Правила, чтобы проверки не враньём занимались

* **Состояние читаем живьём.** `probe.economy.metaOf(player)` / `peekWallet(id)` /
  `probe.economy.getTunables()` / `probe.spawn.spawnProtectActive()`, а не `readJson("sw:eco:meta")`.
  Отложенные задачи, которые аудит «догоняет», дёргаем синхронно (`probe.ranks.syncRankTags()`),
  иначе проверка меряет расписание.
* **Никаких абсолютных порогов накоплений мока.** Мок хранит частицы и строки чата вечно;
  `particles > 4000` на 60 игроках — это арифметика прогона, а не баг. Пороги — темп на игрока
  за тик (`lastSample`).
* **Путь обязан дойти до состояния.** Действие, после которого ничего не изменилось, — это не
  «проверка прошла», а «проверка ничего не видела». Поэтому `caseRush`/`rankRoll` сначала
  финансируют игрока, а потом требуют, чтобы крутки и кошелёк сдвинулись.
* **Инвариант, а не строка.** Проверка должна выжить при правке текста (ru/en) и умереть при
  правке поведения.
* **«Никому» значит без обхода по правам:** служебные изменения блоков идут через `grantGrace`
  и не кормят античит, но и не дают игроку сломать защищённое.

## 5. Чего headless-прогон не проверяет

Нужен живой BDS (см. `docs/META.md` §7, `docs/WORLD-MODS.md` §6): видимость fake-player строк
сайдбара, поведение `ObjectiveSortOrder` в рантайме, пересечение action bar'ов, `§`-префикс
ранга после респавна, вода фонтана на реальном движке, `setImpactedBlocks` при `cancel=false`
и цена sweep'а (968 `setBlockPermutation`) на сервере.
